# OmniBrille v1.1.0 public release

This is a historical owner report. Current architecture and release guidance remain authoritative over this snapshot.

## What this run was meant to do

Publish the already-qualified OmniBrille v1.1.0 source from exact commit `6a0199c70d230e5162028b860bad95d8fd12a8cb` as the new stable GitHub release, intentionally unsigned, without moving the tag to later publication-documentation work or overstating manual, hardware, accessibility, Connected, or platform validation.

## What actually changed

OmniBrille 1.1.0 is publicly available from the [GitHub Release](https://github.com/nishdel/OmniBrille/releases/tag/v1.1.0). The Windows x64 installer is self-contained, per-user, and intentionally unsigned. Its SHA-256 is `55ADAE5C5212B368C367FDA4CAB0C9CFC6AF06D0E34D69145F77C17A2D2364F2`.

The exact release commit first reached GitHub `main` through a normal fast-forward. A fresh unsigned release workflow then rebuilt and proved the pinned DNG-free native dependency, ran the clean repository release verifier, produced one five-file artifact set, and exercised that exact installer on a separate checkout-free Windows runner. An annotated `v1.1.0` tag was created only after those gates passed and peels to the release commit. The stable release contains the installer, checksum, manifest, dependency inventory, generated artifact notes, and lifecycle validation record. The native proof remains retained with the workflow rather than being presented as an ordinary-user download.

Repository documentation was updated afterward on `main` only for publication status, download links, evidence, and limitations. The tag and release artifact manifest remain bound to `6a0199c70d230e5162028b860bad95d8fd12a8cb`.

## Important technical decisions

- **Decision →** Run a new unsigned release-candidate workflow from exact GitHub `main` rather than reuse an earlier local or ordinary-CI installer. **Why →** installer timestamps make separate builds byte-distinct, and the release must keep installer, sidecar, manifest, notes, and validation evidence together. **Impact →** workflow run [33903700910](https://github.com/nishdel/OmniBrille/actions/runs/33903700910) is the sole source of the six public assets.
- **Decision →** Publish unsigned after explicit owner acceptance. **Why →** no signing credentials or approved certificate were available or requested. **Impact →** installer, installed application, and metadata report `NotSigned`; every public download surface retains the Unknown Publisher/SmartScreen warning, and SHA-256 is described only as byte-integrity evidence.
- **Decision →** Keep `v1.1.0` on the qualified source commit and place status/link corrections in a later documentation-only commit. **Why →** moving the tag would invalidate the artifact's exact commit provenance. **Impact →** source archives and manifest agree on `6a0199c70d230e5162028b860bad95d8fd12a8cb`, while current `main` may advance only for release-status truth.
- **Decision →** Proceed under the owner's explicit publication instruction while leaving unperformed manual gates unchecked and excluding them from public claims. **Why →** automated qualification cannot prove visual quality, real screen-reader/microphone/audio/GPU/DPI behavior, or a current live Connected host. **Impact →** v1.1.0 is stable and downloadable under a Windows x64 Standalone contract, but publication is not represented as evidence for those narrower boundaries.

## What the agents learned

- **Remain candidate:** add an explicitly post-publication-safe generated-notes mode in a future version. This run exposed a recurring tension between immutable pre-publication artifact generation and status wording, but changing the frozen release commit or altering one validated asset would have been more harmful than clarifying its role on the release page.
- **Retained:** a final release should use one newly generated hosted artifact family and one exact workflow run as authority. The existing manifest, sidecar, workflow identity, artifact-only consumer, and public hash verification supplied independent evidence, so no new process rule was needed.
- Architecture/release-security, Documentation, and adversarial validation concerns were necessary. Product strategy, renderer implementation, performance implementation, and AX routing were unnecessary because no product behavior or source code changed during publication.
