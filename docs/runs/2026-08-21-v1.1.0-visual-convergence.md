# OmniBrille v1.1.0 visual convergence

This is a historical owner report. Current architecture and release guidance remain authoritative over this snapshot.

## What this run was meant to do

Converge OmniBrille's implemented Windows experience on the owner's graph-first visual direction without redesigning its product architecture, then qualify and publish the result only if the existing high-risk renderer, UX, accessibility, performance, and release gates passed.

## What actually changed

OmniBrille now has a graph-first application shell: the bounded graph fills the client area while navigation, mode, Search, zoom, status, voice, and utility controls use compact floating surfaces. Search is collapsed until requested, the current-focus summary is concise, and Details, Search results, and the accessible list read as integrated graph overlays. The renderer gives the real central focus and already-admitted depth bands a clearer visual hierarchy without changing graph admission, coordinates, navigation, provider state, protocol behavior, or the 48-node/84-edge budgets. Dark and Light presentation, reduced motion/effects, DataRain, keyboard paths, automation names, and graph/list parity remain part of the same implementation.

The work also corrected a pre-existing first-run composition defect: Welcome and the bottom status surface could visually cover Settings or another secondary panel at the minimum window size. One shell visibility authority and focused headless tests now keep those surfaces mutually clear.

Five real Windows screenshots were recaptured from an installed v1.1 candidate using non-private public demo data. The public README deliberately continues to download the immutable published v1.0.0 release and labels the new images as a v1.1 candidate. v1.1.0 is not published.

## Important technical decisions

- **Decision →** Treat the work as v1.1.0, not as replacement bytes for v1.0.0. **Why →** the published v1.0 tag, release, artifact hash, and exact qualification are immutable evidence; this is a substantial visual change rather than a narrow patch. **Impact →** v1.0 remains untouched and downloadable while v1.1 follows a new full release gate.
- **Decision →** Preserve native window chrome and all existing state owners. **Why →** custom chrome and shell-local navigation/Search state would add DPI, keyboard, accessibility, and architectural risk without being required by the supplied visual direction. **Impact →** the change is a presentation convergence, not a new windowing or session architecture.
- **Decision →** Strengthen hierarchy through discrete, bounded presentation policy and cached drawing primitives. **Why →** existing layouts already carry truthful focus, depth, role, and opacity information. **Impact →** no extra filesystem enumeration, fabricated graph structure, unbounded renderer resource path, or new animation loop was introduced.
- **Decision →** Stop before hosted qualification or publication. **Why →** permission to push this candidate branch was not established, and the owner's prior unsigned authorization applied to v1.0.0 rather than v1.1.0. **Impact →** local evidence is retained, but no public branch, tag, release, or asset was changed.

## Problems found

The initial visual captures inherited local reduced-effect preferences and therefore did not represent default presentation. They were discarded and all five images were recaptured from an installed candidate after native UI Automation confirmed the default settings. Independent minimum-size review then found the pre-existing Welcome/status overlap; the visibility authority, ordering, panel bounds, and regression coverage were corrected and re-inspected. A shallow UI Automation probe initially appeared to miss Settings descendants, but recursive comparison against both v1.0 and v1.1 proved the controls were present; no false product fix was made.

No product, renderer, performance, licensing, or packaging blocker remains in the locally qualified v1.1 candidate. Publication remains paused at two explicit boundaries: no authorization to push this branch for hosted qualification, and no v1.1-specific signed-versus-unsigned release decision.

## What the agents learned

- **Promoted:** a stable release-version fallback must be executable memory rather than a release-note convention. An overlooked Inno fallback still said 1.0.0; it was corrected to 1.1.0 and protected by `PackagingMetadataTests`.
- **Promoted:** first-run secondary surfaces must own their visual space at the minimum window size. Independent native inspection supported one visibility authority plus headless Welcome/Settings/list/Search/connection regression coverage.
- **Remain candidate:** add a small orientation-focused edge-drawing test if endpoint styling is changed again. Current endpoint math is symmetric and directly reviewed, so a new private-renderer seam was not justified in this run.
- **Rejected:** turn the inherited-preference screenshot mistake into a global agent rule. Screenshot provenance now records source, installer, display conditions, demo data, and default effect state; another broad instruction would duplicate that durable mechanism.
- **Rejected:** classify the shallow UI Automation result or the picker harness limitation as a product defect without reproducible application evidence.
- UX/visual, Architecture/accessibility/release, Performance, Implementation, Documentation, and independent Adversarial Review were useful for this high-risk change. Product strategy and AX specialists were unnecessary because product scope and AI-assisted behavior did not change.
