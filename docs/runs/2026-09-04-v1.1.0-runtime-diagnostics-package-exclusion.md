# v1.1.0 exact-installer runtime-diagnostics exclusion

## What this run was meant to do

Qualify the exact clean v1.1.0 installer after the Voice start authority-race correction, including fresh local install and an in-place upgrade from the checksum-bound public v1.0.0 predecessor.

## What actually changed

The first fresh installed-artifact check found `mscordaccore_amd64_amd64_8.0.2926.32403.dll` in the newly rebuilt v1.1 payload. That diagnostics-only DAC family had already been classified as an obsolete v1.0 installer-owned file, but the current self-contained .NET runtime pack supplied a servicing-specific copy during publish. The installer deletion rule ran before file installation and therefore could not keep a newly packaged copy out of a fresh install.

Windows packaging now removes only `mscordaccore_*.dll` from the freshly published root. The public-release verifier rejects the family in the payload, and the hosted artifact-only lifecycle independently rejects it after install. The existing installer deletion rule remains the narrow upgrade cleanup for the public v1.0.0 copy.

## Important technical decisions

- **Decision:** Exclude the known diagnostics-only family during package construction. **Why:** it is not required to run OmniBrille, v1.1 documentation already identifies it as obsolete, and an install-time delete cannot exclude a file that the same installer subsequently copies. **Impact:** fresh and upgraded v1.1 installations converge on the same intended payload without broad directory deletion.
- **Decision:** Enforce absence both before installer construction and after hosted installation. **Why:** runtime-pack servicing can change publish contents, while installer ordering can change installed contents. **Impact:** either regression fails the release pipeline at the boundary where it appears.

## Validation and confidence

**Verified before the correction:** exact installer/manifest/sidecar agreement for predecessor candidate `3c9e0fd17decc7367a8be9172885ddd33932e6ac`; 287 passing automated tests; warning-free Release build; no known vulnerable packages; local fresh install reproduced the unexpected file; failure cleanup removed the installation and restored owner preferences.

**Not verified in this snapshot:** the corrected clean commit, rebuilt installer, fresh/install-upgrade lifecycle, hosted CI/release-candidate workflows, and all manual/hardware/Connected/accessibility gates. Those must run against the later exact commit.

**Inferred:** the file is diagnostics-only and safe to omit based on its DAC identity and the already intended v1.1 package contract; launch/relaunch and complete installed lifecycle are still required to prove the actual corrected artifact.

## Problems found

Fixed in source: runtime-pack servicing could silently defeat the documented v1.1 payload cleanup. The original release verifier did not reject the file, allowing its package gate to pass; the new pre-package and post-install assertions close both detection gaps.

## What the agents learned

Upgrade deletion and fresh payload exclusion are separate contracts because Inno Setup processes `[InstallDelete]` before `[Files]`. A source-level installer rule was insufficient evidence; the exact fresh installed artifact exposed the ordering problem. The durable forms are the packaging exclusion and two release assertions rather than a new global instruction.
